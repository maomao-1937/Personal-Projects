# 第 1 阶段技术开发文档｜动态案件与确定性审讯后端

> 配套文档：`AI审讯室-竞品参考PRD.md`、`AI产品Vibe Coding通用技术栈手册.md`、`docs/技术适配声明.md`。

## 一、阶段目标

- 交付范围：LLM 动态案件、固定案回退、匿名 Session、最多 8 回合审讯、角色模型回答、证据命中、结案门槛与确定性评分。
- 阶段产物：FastAPI 服务、OpenAPI、SQLite 持久化、pytest 测试、无秘密配置样例。
- 验收标准：正确证据命中有效；无关证据、重复问题、无证据持续施压均不降低防线；第 3 回合前不能结案；第 8 回合后必须结案；相同报告得分一致；错误报告仍返回完整真相。
- 明确不做：登录、支付、多人、语音、地图探索、分享图片和云部署。
- 主链路：读取案件 → 创建 Session → 提交多轮问题 → 达到报告门槛 → 提交结构化报告 → 返回评分与真相。

## 二、技术适配摘要

- 采用默认方案：FastAPI、Pydantic、pytest、`/api/v1`、固定代码状态机。
- 启用按需模块：SQLAlchemy、SQLite、Alembic，用于 Case Snapshot、Session、回合请求和报告持久化与幂等。
- 模型边界：生成模型输出完整结构化案件；角色模型只表演已由规则层决定的回合结果。
- 开发路径：后端先行。

## 三、技术栈与模型

- Python 3.11、FastAPI、Pydantic v2、SQLAlchemy 2、Alembic、pytest、httpx。
- 模型：`qwen3.6-plus` 生成 Case Snapshot，`qwen-plus-character` 生成嫌疑人措辞；两者均通过 OpenAI-compatible API 调用。
- 运行时生成只调用一次案件模型，然后通过 Pydantic JSON Schema、12+ 内容硬门槛、引用完整性、证据可达性和权重上限进行程序校验；图元数据与降级回答模板由服务端规范化。

## 六、数据、资产与状态

- `sessions` 表：`id`、`case_id`、`stage`、`state_json`、`report_json`、`revision`、`created_at`、`updated_at`。
- `cases` 表：保存生成后不可变的完整 Case Snapshot；公开 API 投影会排除真相、谎言节点、软肋和回答模板。
- `turn_requests` 表：`session_id` + `request_id` 唯一定位一次回合提交，并保存该次结构化响应；客户端超时后使用同一 `requestId` 重试，不会重复消耗回合。模型调用前先写 pending 占位，短暂等待并发请求的首次结果；进程崩溃遗留的占位在 120 秒后可被接管。
- 事务边界：每次回合与报告提交使用 revision 条件更新；过期写入返回 `SESSION_CONFLICT`，不能覆盖新状态。
- Session 状态：`turnCount`、`defense`、`hostility`、`defenseBand`、`selectedEvidenceId`、`discoveredEvidenceIds`、`effectiveEvidenceIds`、`hitLieNodeIds`、`claims`、`messages`、`canSubmitReport`；JSON 读取经过显式版本迁移链。
- 状态流转：`briefing → interrogation → report_required/report_ready → completed`。
- 报告提交幂等：已完成 Session 再提交时返回第一次结果。

## 七、API 设计

| 方法 | 路径 | 作用 | 主要错误 |
| --- | --- | --- | --- |
| GET | `/api/v1/health` | 健康检查 | 无 |
| GET | `/api/v1/cases/001` | 返回公开案件数据 | `CASE_NOT_FOUND` |
| POST | `/api/v1/cases/generate` | 生成、校验并封存新案 | `LLM_NOT_CONFIGURED`、`CASE_GENERATION_FAILED` |
| POST | `/api/v1/cases/fallback` | 显式返回手工精修案 | 无 |
| GET | `/api/v1/cases/{caseId}` | 返回指定案件的公开投影 | `CASE_NOT_FOUND` |
| POST | `/api/v1/sessions` | 创建匿名 Session | `CASE_NOT_FOUND` |
| GET | `/api/v1/sessions/{id}` | 恢复 Session | `SESSION_NOT_FOUND` |
| POST | `/api/v1/sessions/{id}/turns` | 携带 `requestId` 提交一回合，可安全重试 | `INVALID_TURN`、`TURN_LIMIT_REACHED`、`SESSION_CONFLICT` |
| POST | `/api/v1/sessions/{id}/reports` | 提交报告并评分 | `REPORT_LOCKED`、`INVALID_REPORT` |

错误统一为：`{"error":{"code":"...","message":"..."}}`。

## 八、回答模板与规则

- 规则层先决定证据效果、防线、解锁和局部承认，角色模型再在允许事实范围内改写回答；Prompt 只发送已公开事实，不发送完整真相、隐藏证据、未命中谎言或私密软肋正文。
- 角色模型超时、返回过长、提前认罪或越界时，自动使用服务端受控模板，不回滚规则结果。
- 回答 2–4 句，不引入未登记的人物、数字和证据。
- 正确证据 + 正确主题击中对应谎言节点；同一节点只首次生效。
- 普通问题、防线变化、证据解锁和自动笔记均由纯函数计算。

## 九、验收界面

本阶段先用 API 自动化测试和 OpenAPI 验证，不创建平行临时页面；正式 Next.js 前端紧接本阶段，并复用同一 API。

## 十、测试要求

- 规则单测：有效命中、无关证据、重复问题、空问题、超长问题、共情软肋、无证据施压、8 回合上限。
- 门槛单测：第 3 回合、2 条证据、1 次有效命中缺一不可。
- 评分单测：正确报告、部分正确、错误报告、幂等提交、完整真相。
- API 集成：创建、恢复、回合、相同 `requestId` 重试、并发写冲突、报告、404 和 422。
- 真实模型冒烟：校验生成 5 条证据 / 3 个谎言节点的动态案，并用可达公开证据命中一个节点，角色模型返回合法文本。

## 十二、风险与待确认项

- SQLite 只适合当前匿名早期版本；生产多用户并发前迁移 PostgreSQL。
- 本地开发由 `app.main:app` 在单进程 lifespan 中自动迁移；生产环境必须先单独执行 `alembic upgrade head`，再启动禁用自动迁移的 `app.production:app`。
- 正式公网发布前补齐 API 网关限流、匿名 Session TTL 与过期数据清理；当前未将其伪装为已完成能力。
- 本地预设回答验证的是规则与交互，不代表真实 LLM 的角色稳定性。
- 必须由产品经理决定的问题：无。
