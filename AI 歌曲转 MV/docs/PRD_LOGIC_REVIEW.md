# 《AI 歌曲转 MV》PRD V1.0 逻辑审查

> 审查日期：2026-08-28  
> 审查范围：PRD V1.0、4i 竞品拆解 01—09 与 evidence、三份技术栈手册、当前仓库代码、README、测试脚本和既有检查结论  
> 审查目的：修正产品逻辑，为后续分阶段复现做准备；本轮不修改业务代码

## 1. 结论

PRD V1.0 的产品方向和主链路正确，也已经识别了导出版本、部分成功和 Provider 抽象等关键问题，但仍存在可实施性和状态一致性缺口。最主要的问题是：把完整 P0 当作“一天上线版”、Storyboard 与 Cut 边界不清、Beat 分析进入分镜的规则不够确定、Preview/Export 缺少不可变版本快照、任务恢复只写了目标而未定义行为，以及数据模型未覆盖 StoryboardVersion、TimelineVersion、Artifact 和 Preview。

这些问题均已在 `AI歌曲转MV_PRD_V1.1.md` 中修正。V1.1 保留完整 P0 主链路，但将“一天”限定为技术闭环验证，不再承诺一天完成可上线 P0。

## 2. 审查依据与证据边界

- 4i 已观察到：上传、分析等待、Director、Plot、Storyboard/Segment、Cut 独立生成、部分成功预览、编辑器 Timeline、Preview、Export、项目列表和账户入口。
- 4i 未观察或未完成验证：注册闭环、付费闭环、积分扣费准确规则、最终删除结果、失败退款、重新生成版本保留规则。
- 4i 页面未展示 BPM、Beat、Onset、Mood、Energy 等音乐分析值，因此 V1.1 中的 BPM/Beat/Onset/Energy 逻辑来自当前项目已验证的 librosa 能力，不冒充竞品事实。
- evidence 证明 4i Timeline Export 曾复用旧 Director 导出内容。V1.1 明确禁止沿用这一行为。

## 4. 当前仓库的真实能力与缺口

### 4.1 已验证可保留的能力

- `librosa` 实现 BPM、Beat、Downbeat（按 4/4 近似）、Onset Strength、RMS Energy 和时长分析。
- Beat Sync 会按 Energy、Onset 和 Downbeat 对节拍评分，并生成卡点切换位置。
- FFmpeg 以 H.264/AAC 输出 MP4，并使用单次 `filter_complex` 拼接视频段。
- FastAPI 已提供启动任务、SSE 进度和 MP4 下载接口；进度来自真实后台处理，不是前端假动画。

### 4.2 必须在阶段 1 解决的工程约束

| 现状 | 仓库事实 | V1.1 约束 |
|---|---|---|
| 任务只在内存 | `job_store.py` 使用进程级字典和 `asyncio.Queue` | Job、事件序号和结果必须持久化；服务重启后可查询和恢复 |
| SSE 中断后卡住或重复 | SSE 先重放所有日志，再消费单一 Queue；前端 `onerror` 仅关闭连接 | 增加事件序号、快照查询、自动重连和日志去重；SSE 不作为事实源 |
| 非法参数可能返回 500 | 表单参数进入 `ProcessSettings` 时未统一转换为 4xx | 所有输入经 Pydantic/业务校验，非法输入稳定返回结构化 4xx |
| Mac 下载路径不完整 | yt-dlp 的 Node 路径写死为 Windows 路径；FFmpeg 场景检测输出也使用 `NUL` | P0 不依赖 YouTube；保留能力时必须做跨平台配置与测试 |
| 缺少可靠测试和 CI | 现有 `test_pipeline.py` 是依赖 YouTube 的手工脚本，无 pytest 用例，无 `.github` CI | 建立单元、接口、恢复、版本与真实模型冒烟测试；增加 CI |
| 文档和版本不一致 | README 写后端未实现；标签/结论、API、前端版本分别为 2.0.1、2.0.0、0.0.0 | 单一版本来源；README、API 和发布记录同步 |
| 文件上限过宽 | 当前后端最大上传 2 GB | 新产品 P0 收敛为 100 MB 和 60 秒，且上传前后都校验 |
| 文件落在本地目录 | uploads/output 位于服务本地磁盘 | 开发期可本地；上线前必须切换持久对象存储并配置清理策略 |

## 5. 已采用的推荐方案

- P0 音频：MP3/WAV，30—60 秒，最大 100 MB；FLAC 放入 P1，待跨平台样本验证后开启。
- P0 初始 Storyboard：4—12 个 Cut，默认目标 4—6 秒；最终数量由音频时长、BeatPlan 与 VideoProvider 支持时长共同确定。
- Cut 并发：单项目最多 2 个视频生成任务并发，默认最多 12 个初始生成任务；均可由后端环境变量调整。
- Preview：后端 FFmpeg 生成、绑定 timeline_version；部分成功时使用明确占位片段，但不得正式导出。
- Regenerate：成功前保留当前 active 资产；新资产成功后自动切换为 active，旧资产保留为上一版本用于审计/回退。
- 导出：16:9 与 9:16 为两个独立任务；9:16 第一版使用确定性中心裁切/缩放安全区策略，不调用第二次视频生成模型。

## 6. 已确认的产品决策

产品经理于 2026-08-28 确认按推荐方案执行：

1. **P0 音频时长上限**：60 秒，P0 不扩展到整首 3—5 分钟。
2. **单项目视频生成预算**：首次最多 12 个 Cut，单项目最多 2 个视频生成任务并发。
3. **生产资产保留期**：项目最后活动后保留 30 天；临时文件保留 24 小时；被替换且非 active 的资产保留 7 天。

以上三项不再是待确认事项。若后续调整，必须作为范围、成本与数据承诺变更重新评审。

## 7. 阶段结论

V1.1 完成后必须停在阶段 0。未收到“PRD V1.1 已确认，API Key 已配置，开始后端阶段”前，不得修改业务代码、安装依赖、调用真实模型、开发正式前端或部署。
