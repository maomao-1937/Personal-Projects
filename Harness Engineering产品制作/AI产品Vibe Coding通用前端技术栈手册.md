# AI Agent 产品 Vibe Coding 通用前端技术栈手册

> 文档版本：V1.0  
> 适用对象：产品经理、AI 产品经理、设计师、Vibe Coding 执行者、前端开发者、代码型 AI Agent  
> 默认范围：Web 端 AI Agent 产品的 MVP；兼顾已有项目迭代  
> 配套输入：产品 PRD、后端技术栈手册、接口文档或接口草案、分阶段开发文档、设计稿或视觉参考（如有）

阅读建议：产品经理重点阅读第 0、22、25、26 节，其余内容主要交给 AI 完整读取。

---

## 0. 先说结论：这份手册怎么用

本手册是三份手册（通用 → 前端 → 部署）中的**第 ② 份**，在 MVP 核心链路验证通过后使用；完整旅程见《AI Agent 产品 Vibe Coding 通用技术栈手册》开头的总地图。

产品经理不需要先学会前端开发。

在一个新产品中，把以下资料一起交给 AI：

1. 产品 PRD；
2. 本前端手册；
3. 后端通用技术栈手册；
4. 已有代码、接口文档、设计稿或参考产品（有就提供，没有也可以）；
5. 本阶段希望完成的业务目标。

AI 应先输出两份短文档：

- 《前端技术适配声明》：说明本项目采用什么、为什么、哪些地方偏离默认方案；
- 《本阶段前端开发文档》：说明本阶段做哪些页面、组件、接口、状态和验收。

产品经理确认后，再进入 Vibe Coding。

如果产品经理已经提供了分阶段开发文档，AI 不应重复另写一套，而应先检查它是否覆盖本手册要求，再补齐缺项。

一句话工作流：

```text
PRD + 前端手册 + 后端手册 + 项目资料
                    ↓
          AI 输出前端适配声明
                    ↓
          AI 输出/校验阶段开发文档
                    ↓
        按“可运行的业务闭环”分阶段开发
                    ↓
      浏览器真实预览 + 自动检查 + 人工验收
```

本手册的目标不是让所有产品长得一样，而是让 AI 在面对不同 Agent 产品时，有一套稳定的前端决策顺序、工程底线和验收方法。

本手册也不能替代 PRD 和接口契约。最少需要明确：用户是谁、核心任务是什么、成功结果是什么、后端能提供什么。如果这些信息缺失，AI 可以先做原型，但不能把它当作完成真实产品开发。

### 产品经理在前端阶段的分步操作（AI 逐条转述）

1. **第一步：给视觉方向**——可以是设计稿、参考产品截图、或一个设计系统网址；都没有的话，我按中性方案先做一版代表页。
2. **第二步：看代表页反馈**——对颜色、圆角、密度、字体提意见，我改到你满意再铺开全站，避免改错返工。
3. **第三步：逐阶段验收**——我每完成一个页面/闭环，给你"照着点"的清单（打开哪个地址、点哪几步、看什么状态），你照做并把异常截图给我。
4. **第四步：真机验证**——语音/麦克风/录音等能力，需要你用真机（含 iPhone）走一遍，把现象告诉我。

## 1. 本手册解决什么问题

普通技术栈清单只会告诉 AI“使用 Next.js、React、Tailwind CSS”。这远远不够。

AI Agent 产品的前端还要处理：

- 一个任务可能运行几秒、几分钟甚至更久；
- 生成过程可能持续输出文本、步骤、日志和中间结果；
- Agent 可能暂停，等待用户确认或补充资料；
- 页面刷新、断网或关闭后，任务仍可能在后端继续运行；
- 同一个任务可能产生图片、视频、音频、文件等不同产物；
- 接口成功不等于产品成功，用户必须看得懂当前发生了什么；
- 桌面端能用，不代表移动端、键盘操作和异常状态能用；
- “构建成功”不等于“页面已经达到交付标准”。

因此，本手册同时规定四件事：

1. 默认技术栈；
2. 前端架构和数据边界；
3. Agent 交互与任务状态规范；
4. 开发、预览和验收规范。

---

## 2. 适用边界

### 2.1 默认适用

- AI 对话、内容生成、工作流、自动化和多媒体生成产品；
- 内部工具、运营后台、创作工作台、Agent 控制台；
- 面向桌面浏览器，兼顾移动浏览器的 Web MVP；
- 从零创建的新项目；
- 已有 React 或 Next.js 项目的功能迭代。

### 2.2 可以参考，但不能直接照搬

- 原生 iOS、Android、鸿蒙应用；
- 微信小程序、桌面客户端、浏览器插件；
- 对搜索引擎收录、极致首屏速度有特殊要求的大型内容站；
- 高实时协同编辑、3D、游戏、超大数据可视化产品；
- 受医疗、金融、政务等强监管约束的系统。

遇到这些场景，仍需遵守本手册的状态、安全和验收原则，但 AI 必须重新给出技术适配声明，不能机械套用 Web 默认栈。

## 3. 信息优先级：资料冲突时听谁的

当不同资料互相冲突时，AI 按以下顺序判断：

1. 产品经理本轮明确提出并确认的目标；
2. 已确认的 PRD 和验收标准；
3. 已确认的设计稿、设计系统和交互说明；
4. 已确认的接口契约和后端真实能力；
5. 现有项目代码、框架和工程约束；
6. 本手册的默认建议。

但以下内容不能因为 PRD 没写就忽略：

- 安全和隐私底线；
- 加载、空、失败和恢复状态；
- 移动端基本可用；
- 核心流程的真实浏览器验收；
- 不得在前端暴露密钥；
- 不得把本地界面状态冒充为后端真实任务状态。

如果资料存在关键冲突，AI 应在编码前用产品语言说明冲突、影响和推荐方案。不要在代码中偷偷选择。

## 4. 决策分层：哪些必须统一，哪些按项目选择

### A 层：所有项目都必须遵守

- 使用 TypeScript，并开启严格类型检查；
- 接口调用集中管理，不在页面组件中散落 `fetch`；
- 后端是任务状态和业务结果的最终事实来源；
- 加载、空、成功、失败、等待确认、断线恢复等状态必须被设计；
- 密钥、服务商凭证、私密系统提示词不能进入浏览器；
- 核心页面必须支持合理的桌面端和移动端布局；
- 核心操作可被键盘完成，交互控件有可理解的名称；
- 重要提交必须防重复，重要删除必须确认；
- 必须通过代码检查、构建检查和真实浏览器验收；
- 不能只用 Mock 数据宣布“前后端已经完成”。

### B 层：Web MVP 默认方案

- Node.js 当前活跃 LTS 版本；
- npm 作为默认包管理器；
- Next.js 稳定版本，使用 App Router；
- React 与 Next.js 官方支持的稳定版本；
- TypeScript strict 模式；
- Tailwind CSS + CSS 语义变量；
- Lucide 图标；
- Vitest + React Testing Library；
- Playwright 覆盖核心业务闭环；
- ESLint、类型检查、生产构建作为交付门槛。

小云雀当前可验证的参考基线是 Node.js 22、Next.js 16、React 19、Tailwind CSS 4。新项目不应永久锁死在这些大版本上，而应在《前端技术适配声明》中记录创建项目时实际使用的稳定版本，并锁定依赖文件。

### C 层：出现明确需求后再引入

| 能力 | 建议方案 | 引入条件 |
|---|---|---|
| 无障碍复杂组件 | Radix UI 或基于它的 shadcn/ui | 对话框、菜单、下拉框等组件较多 |
| 服务端数据缓存 | TanStack Query | 多页面共享请求、缓存、失效和重试变复杂 |
| 全局客户端状态 | Zustand | 多个远距离组件共享临时状态，URL 和组件提升都不合适 |
| 复杂表单 | React Hook Form + Zod | 动态字段、多步骤表单、复杂校验 |
| 接口代码生成 | OpenAPI Generator 等 | 后端已有稳定、可持续维护的 OpenAPI 契约 |
| 大列表虚拟化 | TanStack Virtual 等 | 实际数据量造成明显卡顿 |
| 富文本或代码编辑器 | 按业务选型 | PRD 确实需要编辑能力 |
| 图表、画布、流程编排 | 按业务选型 | PRD 出现对应交互，不提前预装 |
| 国际化 | 成熟 i18n 方案 | 已确认多语言需求 |
| PWA、离线能力 | Service Worker 方案 | 已确认离线或安装需求 |
| 前端错误监控 | Sentry 等 | 产品进入真实用户测试或生产环境 |
| 产品行为分析 | 合规的分析工具 | 已有指标方案和用户授权策略 |

原则：没有真实复杂度，就不要用复杂工具制造“看起来专业”的代码。

## 5. 默认技术选型

### 5.1 应用框架：Next.js App Router

默认选择 Next.js，而不是自己拼装 React 路由、构建、服务端渲染和部署能力。

适合 Agent 产品的原因：

- 页面路由、布局和服务端能力在同一个工程中；
- 可以按页面决定服务端组件和客户端组件；
- 方便实现同源 API 代理、鉴权入口和部署；
- 生态成熟，AI 对代码结构和常见问题的识别能力较强。

以下情况可以改用其他方案：

- 已有项目已经稳定运行在其他框架；
- 产品只需要一个很小的嵌入式页面；
- 部署平台对框架有明确限制；
- 原生端或小程序不是 Web 技术路线。

AI 不得仅为了“追新”而替换已有稳定框架。

### 5.2 语言：TypeScript strict

最低要求：

- 核心业务类型不使用 `any` 逃避检查；
- 外部接口返回值在进入业务层前被约束或校验；
- 组件 Props、任务状态、产物类型、错误类型有清晰定义；
- 使用 `unknown` 接住不可信数据，再逐步缩小类型；
- 类型错误不能以“先忽略”为交付方案。

TypeScript 只能检查开发时类型，不能证明后端实际返回的数据正确。关键外部数据仍需运行时校验或安全的字段兜底。

### 5.3 样式：Tailwind CSS + 语义化设计变量

Tailwind CSS 负责快速布局和原子样式，CSS 变量负责统一设计语言。

颜色、圆角、阴影、间距等应尽量表达语义，例如：

```css
:root {
  --color-bg: #ffffff;
  --color-surface: #f7f8fa;
  --color-text: #18202a;
  --color-muted: #667085;
  --color-primary: #5b5ce2;
  --color-danger: #d92d20;
  --radius-card: 16px;
}
```

不要让页面各处直接散落无法解释的颜色值，也不要把 Tailwind CSS 本身当成完整设计系统。

### 5.4 组件策略

默认顺序：

1. 先复用当前项目已有组件；
2. 再使用原生 HTML 和轻量自建组件；
3. 复杂交互组件使用成熟的无障碍基础组件；
4. 只有确有必要时才引入完整组件库。

组件库解决的是交互基础和开发效率，不负责替产品做视觉设计。

### 5.5 版本策略

- 新项目创建时选择稳定且仍受维护的版本；
- 在 `package.json` 和锁文件中固定实际依赖；
- 同一开发阶段内不主动跨大版本升级；
- 安全修复可以升级，但升级后重新执行完整检查；
- 已有项目优先兼容，不因为本手册的参考版本而强制迁移。

## 6. 默认前端架构

### 6.1 推荐目录

新项目默认使用“路由 + 业务功能 + 通用基础设施”的结构：

```text
frontend/
├── app/                       # 路由、页面、布局、错误页
│   ├── (workspace)/
│   ├── api/                   # 确有需要的同源代理或 BFF
│   ├── error.tsx
│   ├── loading.tsx
│   └── layout.tsx
├── components/
│   ├── ui/                    # Button、Dialog、Input 等通用组件
│   └── layout/                # 顶栏、侧栏、页面容器
├── features/
│   └── task-generation/       # 按业务功能组织
│       ├── api/
│       ├── components/
│       ├── hooks/
│       ├── schemas/
│       ├── types.ts
│       └── utils.ts
├── lib/
│   ├── api/                   # API 客户端、错误归一化
│   ├── stream/                # SSE 或流式响应处理
│   ├── auth/
│   ├── media/
│   └── utils/
├── config/                    # 环境与产品配置
├── styles/                    # 全局样式和设计变量
├── tests/                     # 单元与集成测试
└── e2e/                       # Playwright 核心流程
```

这是一种默认思路，不是强制要求已有项目重构目录。

### 6.2 依赖方向

```text
页面路由
  ↓
业务功能组件与 Hook
  ↓
API / Stream / Auth 适配层
  ↓
后端接口
```

通用 UI 组件不应反向依赖某一个具体业务。页面组件不应直接理解不同后端供应商的特殊字段。

### 6.3 新项目与已有项目的处理

新项目：按本手册默认架构建立基础骨架。

已有项目：先理解已有目录、命名和依赖，再做最小范围改动。除非重构本身是本阶段目标，否则不要一边开发业务，一边大规模迁移目录和组件库。

## 7. 页面渲染与路由选择

### 7.1 Server Component 与 Client Component

Next.js App Router 默认使用 Server Component。

适合 Server Component 的内容：

- 静态说明和帮助页面；
- 首屏即可从服务端获取的数据；
- 不依赖浏览器事件和本地状态的展示；
- 对搜索引擎或分享预览有要求的页面。

适合 Client Component 的内容：

- 表单、拖拽、弹窗和复杂交互；
- Agent 实时进度、流式输出和任务控制；
- 依赖浏览器 API、Local Storage 的功能；
- 高频变化的工作台区域。

不要因为一个按钮就把整页都声明为客户端组件。应把交互边界缩小到必要区域。

### 7.2 URL 是可分享状态的首选

以下状态优先放入路由或查询参数：

- 当前项目或任务 ID；
- 当前工作区、标签页和筛选条件；
- 可以被复制、刷新和恢复的查看位置。

以下状态不适合放 URL：

- 输入框每个按键的临时值；
- 弹窗内部未提交数据；
- 凭证和隐私信息；
- 大体积对象。

刷新页面后，前端应能根据 URL 中的任务 ID 向后端恢复真实状态，而不是依赖内存中残留的数据。

### 7.3 避免 Hydration 问题

浏览器专属信息不能直接参与服务端首次渲染。例如屏幕宽度、Local Storage 和浏览器语言应在客户端安全读取，并提供稳定的首屏默认值。

移动端侧栏、主题和个性化设置必须确保 CSS、React 状态和持久化状态一致，不能出现“按钮显示已经收起，但遮罩或侧栏仍挡住页面”的情况。

## 8. 前端状态管理：先分清四种状态

### 8.1 状态分层

| 状态类型 | 例子 | 默认存放位置 |
|---|---|---|
| URL 状态 | 任务 ID、当前页签、筛选 | 路由或查询参数 |
| 服务端状态 | 任务进度、产物、权限、余额 | 后端；前端通过 API 获取 |
| 页面临时状态 | 输入内容、弹窗开关、局部选中 | 组件 State 或局部 Context |
| 用户偏好 | 主题、侧栏偏好、非关键提示已读 | Local Storage 或用户配置接口 |

### 8.2 事实来源

- 后端任务状态是最终事实来源；
- Local Storage 不能保存并冒充真实任务结果；
- 页面刷新后应重新拉取任务，而不是默认任务失败；
- 同一个任务的不同页面应使用同一个状态定义；
- 前端可以做乐观更新，但失败时必须能回滚。

### 8.3 什么时候引入状态库

默认先使用 React 自带状态能力。

只有出现以下问题时，再引入 TanStack Query：

- 多个页面共享相同服务端数据；
- 请求缓存、失效和重试逻辑重复；
- 列表分页、预取和后台刷新明显复杂；
- 手写请求状态已经难以维护。

只有出现以下问题时，再引入 Zustand 等客户端状态库：

- 多个距离很远的组件共享大量临时状态；
- 状态与 URL、后端数据都无关；
- 通过层层传 Props 已明显降低可维护性。

不要一开始同时引入 Context、Redux、Zustand 和 TanStack Query。

## 9. Agent 产品必须有统一任务状态模型

### 9.1 最低状态集合

一个长任务至少要考虑以下状态：

| 统一状态 | 用户看到什么 | 前端需要做什么 |
|---|---|---|
| `idle` | 尚未开始 | 显示输入和可执行条件 |
| `submitting` | 正在提交 | 禁止重复提交，允许取消请求 |
| `queued` | 已进入队列 | 显示任务已受理，不伪装成正在生成 |
| `running` | 正在执行 | 显示真实进度、阶段或活动提示 |
| `streaming` | 正在持续输出 | 增量展示，避免页面频繁跳动 |
| `waiting_user` | 等待用户确认或补充 | 明确需要用户做什么、为什么 |
| `succeeded` | 已完成 | 展示产物和下一步操作 |
| `partially_succeeded` | 部分成功 | 清楚区分成功项和失败项 |
| `failed` | 执行失败 | 说明发生了什么、是否可重试 |
| `cancelled` | 已取消 | 保留已有信息，允许重新开始 |
| `disconnected` | 连接中断 | 说明任务未必停止，尝试恢复 |
| `stale` | 状态可能过期 | 主动重新获取后端真实状态 |

后端可以使用不同名字，但前端必须在适配层映射成统一含义。未知状态不能静默当成成功或失败，应记录并显示安全的兜底状态。

### 9.2 状态不是一个转圈图标

每个状态都应回答用户三个问题：

1. 现在发生了什么？
2. 我需要做什么？
3. 接下来会发生什么？

例如，“生成失败”不够。更好的表达是：“视频合成失败，已生成的分镜仍然保留。你可以重新合成，不会重复扣除前一步结果。”

### 9.3 加载、空数据和失败必须分开

- `loading`：数据还没回来；
- `empty`：请求已经成功，但确实没有数据；
- `failed`：请求没有成功；
- `permission_denied`：用户无权查看；
- `not_found`：对象不存在或已被删除。

不能在接口尚未返回时先显示“暂无模板”“暂无任务”。这种瞬时错误信息会让用户误以为系统没有数据。

## 10. 流式输出、轮询和断线恢复

### 10.1 选择顺序

| 场景 | 默认方案 |
|---|---|
| 服务端单向持续推送文本或进度 | SSE 或 Fetch Streaming |
| 浏览器与服务端需要双向高频通信 | WebSocket |
| 后端暂时只支持状态查询 | 有节制的轮询 |
| 只需等待一个普通短请求 | 普通 HTTP 请求 |

不要为了“实时感”强行使用 WebSocket。

### 10.2 SSE 注意事项

- 原生 `EventSource` 适合 GET 请求，但不方便设置自定义请求头；
- 需要 POST、请求体或特殊鉴权时，可使用 Fetch Streaming；
- Cookie 鉴权优先通过同源接口处理；
- 某些代理会缓存响应，必须在真实部署链路验证是否逐段到达；
- 页面卸载、任务切换和取消时要关闭连接；
- 断线后应按任务 ID 查询状态，再决定重连，不能盲目重复创建任务。

### 10.3 轮询注意事项

- 使用明确间隔和退避策略；
- 页面不可见时降低频率或暂停；
- 完成、失败、取消后立即停止；
- 避免每个组件各自轮询同一任务；
- 接口失败时不要无限高频重试。

### 10.4 增量展示

- 流式文本要批量刷新，避免每个字符触发复杂重渲染；
- 自动滚动只在用户仍停留在底部时发生；
- 用户向上查看历史内容时，不强行把页面拉回底部；
- 日志、思考过程和用户可见结果要分层，不把内部敏感信息直接展示；
- 断线重连后应去重，避免重复追加相同内容。

---

### 10.5 语音与实时多媒体交互（语音对练 / 语音问答类产品）

当核心交互是**实时语音**时，除了文本流，还要处理"音频流"。链路：

```text
麦克风录音 → 上传 → 后端 ASR 转写 → Agent 生成回复 → TTS 合成 → 音频流回传 → 前端播报
```

前端必须额外处理：

1. **麦克风授权是生死关**：浏览器只在 HTTPS 或 localhost 下开放麦克风权限。授权被拒要给明确引导，不能静默失败；未授权不开始录音。
2. **音频流播报**：后端常通过 SSE 推 base64 PCM 音频分片（`audio` 事件），与文本流（`chunk` 事件）是两条并行流。用 Web Audio API 把分片按时间轴排队播放，避免重叠；会话结束/切换时重置队列。
3. **iOS / Safari 兼容**：`MediaRecorder` 在不同浏览器支持的容器格式不同——Chrome 是 `webm/opus`，iOS/Safari 是 `mp4/aac`。要运行时探测 mime，并把实际格式随上传告诉后端。
4. **交互从简**：MVP 优先"回合制对讲机"（按下说话、再按发送）；全双工 + barge-in 打断是后续阶段。
5. **会后回放**：整段回放 + 逐句点播。音频接口往往要鉴权，`<audio src>` 带不了鉴权头，用"带 token 的 fetch → blob → ObjectURL"加载，用完 `revokeObjectURL`。

**验收**：真实手机（含 iPhone）走一遍录音→播报→回放；会中不出现评分/答案等无关信息；断网或离开页面后已完成轮次仍保留。

## 11. 用户确认、重试、取消和恢复

### 11.1 等待用户确认

当 Agent 等待用户决定时，界面必须展示：

- 当前已经完成了什么；
- 为什么需要确认；
- 可选项及各自影响；
- 默认推荐项；
- 确认后是否可撤销；
- 放弃或返回的方式。

“继续”和“取消”之外，应尽量使用有业务意义的按钮，例如“采用这版分镜并生成视频”。

### 11.2 防止重复提交

- 点击后立即进入明确的提交状态；
- 同一操作在完成前不可重复触发；
- 后端配合使用幂等键；
- 网络超时时，先查询原任务是否已创建，再决定是否重试；
- 禁止用多次点击产生多个昂贵的模型任务。

### 11.3 取消

前端的“取消请求”与后端的“取消任务”不是同一件事。

- 取消浏览器请求：只停止等待；
- 取消后端任务：需要后端提供真实取消能力；
- 如果后端不能取消，按钮应写“停止等待”或“离开页面”，不能误导用户。

### 11.4 恢复

用户刷新页面、关闭页面或重新登录后：

1. 通过 URL 或任务列表找到任务 ID；
2. 向后端查询真实状态；
3. 恢复已有中间结果和产物；
4. 仅在任务仍运行且协议允许时恢复流式连接；
5. 不重复创建同一个任务。

## 12. API 与后端契约

### 12.1 集中式 API 层

页面不直接拼接接口地址。基础 URL、鉴权、超时、错误转换和日志应集中处理。

```text
UI 组件
  ↓ 调用业务函数
Feature API
  ↓ 调用统一客户端
HTTP / Stream Client
  ↓
Backend API
```

这样可以避免：

- 开发环境和生产环境地址散落；
- 普通请求与流式请求使用不同配置；
- 每个页面用不同方式解释错误；
- 后端字段改名导致所有组件同时修改。

### 12.2 最低接口契约

每个接口至少明确：

- 请求方法和路径；
- 请求字段、类型、是否必填；
- 成功返回结构；
- 失败错误码和用户可恢复方式；
- 鉴权与权限要求；
- 是否幂等；
- 超时和重试策略；
- 任务 ID、状态和产物字段；
- 时间、枚举、金额和文件地址的格式。

### 12.3 统一错误结构

前端内部建议将不同接口错误转换成统一结构：

```ts
type AppError = {
  code: string;
  message: string;
  userMessage: string;
  retryable: boolean;
  requestId?: string;
  fieldErrors?: Record<string, string>;
};
```

用户界面显示 `userMessage`，调试日志保留 `code` 和 `requestId`。不要把原始堆栈、供应商报错或敏感请求内容直接展示给用户。

### 12.4 接口类型来源

- 后端已有稳定 OpenAPI：优先生成类型和客户端；
- 契约仍快速变化：先维护清晰的手写类型和适配层；
- 无论哪种方式，生成代码外再保留业务适配层；
- 前后端枚举变化必须有未知值兜底。

### 12.5 环境配置

- 浏览器可读配置可以使用 `NEXT_PUBLIC_`；
- API 密钥、模型密钥、数据库凭证绝不能使用 `NEXT_PUBLIC_`；
- 前端环境只保存公开配置；
- 开发、测试、生产环境地址通过配置管理；
- 普通 API 与流式 API 的地址策略必须一致并经过部署验证。

## 13. 表单、模型配置和输入体验

### 13.1 表单规则

- 必填项、格式、长度和限制在提交前可见；
- 校验错误靠近对应字段；
- 提交失败后保留用户输入；
- 多步骤表单保存草稿或清楚说明离开会丢失；
- 文本框支持合理的粘贴和换行；
- 错误不只用红色表达，还需文字说明。

### 13.2 模型和供应商配置

- 默认模型必须真实存在于可选列表；
- 已保存但暂时不可用的模型要显示“不可用”，不能偷偷切换到第一项；
- 模型名称、能力、成本提示和限制应来自统一配置；
- 配置变化后，当前任务使用了哪个版本应可追溯；
- 用户看不到的内部模型路由不应伪装成用户明确选择。

### 13.3 文件上传

- 上传前说明格式、数量和大小限制；
- 校验扩展名之外，还要依赖后端验证真实类型；
- 显示上传进度、失败原因和重新上传；
- 允许删除或替换尚未提交的文件；
- 大文件使用后端支持的分片或直传方案；
- 私有文件不能依赖永久公开 URL。

## 14. Agent 产物展示

### 14.1 通用产物模型

前端不应只为一种图片结果写死页面。建议统一考虑：

```ts
type Artifact = {
  id: string;
  kind: "text" | "image" | "video" | "audio" | "file" | "json";
  name: string;
  status: "processing" | "ready" | "failed";
  url?: string;
  previewUrl?: string;
  mimeType?: string;
  size?: number;
  createdAt: string;
  metadata?: Record<string, unknown>;
};
```

项目可以扩展，但同一类产物的预览、下载、失败和加载方式应统一。

### 14.2 图片、视频和音频

- 图片有占位、加载失败、放大查看和下载；
- 视频有封面、加载中、播放失败和基本控制；
- 音频有时长、播放状态和下载；
- 多媒体尺寸未知时要预留比例，避免页面跳动；
- 临时 `Object URL` 使用后及时释放；
- 外链资源需要考虑过期、跨域和权限失败；
- 生成中产物不能伪装为最终完成。

### 14.3 结果与调试信息分层

默认界面首先服务普通用户：结果、状态、下一步操作在前。

请求 ID、原始 JSON、详细步骤和日志放入可折叠的“详情”或开发模式。不要把开发调试台直接当成产品界面。

## 15. 设计系统与视觉实现

### 15.1 设计来源优先级

1. 已确认的设计系统和设计稿；
2. PRD 中的品牌、用户和场景要求；
3. 已确认的参考产品，但不得直接复制其受保护资产；
4. 第三方设计系统（产品经理给网址，AI 抓取其中的 DESIGN.md / token）；
5. 本手册的中性默认方案。

如果没有设计稿，AI 应先输出一个简短的视觉方向：颜色、字体、密度、圆角、页面结构和关键组件，再实现首个代表页面供确认。

**第三方设计系统（如 Refero 等风格参考站）**：产品经理可能只给一个网址。AI 应主动用命令行抓取解析，而不是让产品经理口述。注意抓取边界——SSR 页面能直接拿到完整 DESIGN.md；纯 SPA、需登录或反爬的页面可能只能拿到空壳，此时让产品经理把关键截图 + DESIGN.md 文本放进本地目录即可。DESIGN.md 里的颜色/圆角/间距/阴影 token 可直接落为 Tailwind `@theme`。版权上，开源/可商用的设计系统可复用 token，受版权保护的只能借鉴风格。

**字体规则（中文产品必看）**：设计系统自带的字体（Switzer、Basier Circle 等）多为商业字体且不含中文字形，不能直接打包。落地时用官方免费替代（Inter、Plus Jakarta Sans 等）+ 中文系统字体 fallback（PingFang SC / Microsoft YaHei / Noto Sans CJK SC）。`next/font` 加载的字体是构建时自托管，非运行时请求外部 CDN。保留"双字体"思路（正文 + 展示标题），但中文字形统一走系统字体。

### 15.2 最低设计系统

即使是 MVP，也至少统一：

- 主色、背景色、文本色、边框色和状态色；
- 字号层级和行高；
- 4 或 8 像素节奏的间距；
- 圆角和阴影层级；
- 按钮、输入框、卡片、弹窗、提示和标签；
- hover、focus、disabled、loading、error 状态；
- 页面最大宽度和内容密度。

### 15.3 组件层级

- 基础组件：Button、Input、Select、Dialog；
- 复合组件：FileUploader、TaskStatus、ArtifactPreview；
- 业务组件：VideoGenerationForm、WorkflowRunPanel；
- 页面：组织布局和业务流程，不堆积所有底层细节。

不要为了“复用”过早制造需要十几个参数的万能组件。

### 15.4 图标和文案

- 使用统一图标库，不混用多套风格；
- 不用表情符号替代正式功能图标；
- 只有图标的按钮必须有可访问名称和悬停说明；
- 按钮文案使用动作和结果，例如“生成分镜”，不要只写“确定”；
- 状态文案使用产品语言，不暴露内部技术术语。

## 16. 响应式与移动端

### 16.1 默认验收宽度

如 PRD 未另行规定，至少检查：

- 390px：常见手机宽度；
- 768px：平板或窄窗口；
- 1280px：常见桌面工作区；
- 1440px：较宽桌面。

### 16.2 移动端规则

- 桌面侧栏在手机上应变成抽屉或底部导航；
- 抽屉关闭时不能残留透明遮挡层；
- 弹窗在小屏幕可滚动，主要操作始终可触达；
- 表格优先改成卡片、分组或横向受控滚动；
- 固定宽度媒体不得撑破屏幕；
- 触控目标建议不小于 44×44px；
- 键盘弹出时，输入框和提交按钮不能完全被遮挡；
- 页面不得出现无意的横向滚动。

响应式不能只看首页。核心业务流程的每一个页面和弹窗都要检查。

## 17. 无障碍基础要求

- 使用语义化 HTML；
- 所有表单项有关联 Label；
- 所有核心操作可以用键盘完成；
- 焦点位置清晰，弹窗有焦点约束并能正确返回；
- 状态不能只依靠颜色；
- 图片有合适的替代文本，装饰图标不重复朗读；
- 文本和背景有足够对比度；
- 动画尊重用户“减少动态效果”设置；
- Agent 关键进度可使用适度的 live region，但避免每个 Token 都被朗读；
- 错误提示可以被辅助技术识别并定位到字段。

无障碍不是上线前最后补一个插件，而是组件设计的一部分。

## 18. 安全与隐私底线

### 18.1 禁止放入前端

- 模型服务 API Key；
- 数据库密钥；
- 第三方服务私钥；
- 私密系统提示词；
- 后端管理员凭证；
- 只应服务端知道的业务规则。

### 18.2 鉴权

- Web 应用优先使用安全、HttpOnly、SameSite 合理配置的 Cookie；
- 不建议将长期访问令牌放入 Local Storage；
- 同时考虑 CSRF、XSS、会话过期和跨设备退出；
- 权限判断必须由后端执行，前端隐藏按钮不等于权限控制。

### 18.3 内容安全

- 用户或模型生成的 HTML 默认视为不可信；
- Markdown 渲染需限制危险标签和链接；
- 外部链接明确打开行为，必要时增加安全属性；
- 文件名、富文本和 URL 不能直接拼入 DOM；
- 日志、埋点和报错中避免记录完整提示词、隐私文件和密钥。

### 18.4 高成本操作

涉及真实扣费、发布、群发、删除、覆盖和外部系统写入时：

- 前端明确展示影响；
- 用户进行最终确认；
- 后端再次校验权限和幂等性；
- 页面保留结果或审计入口。

---

## 19. 性能原则

- 先测量，再优化；
- 首屏不加载当前页面用不到的大型库；
- 富编辑器、图表、视频工具等按需加载；
- 图片使用合适尺寸、格式和懒加载；
- 为图片和媒体预留空间，减少布局跳动；
- 大列表分页或虚拟化；
- 流式内容采用节流或批量更新；
- 避免相同接口被多个组件重复请求；
- 不把大型二进制文件长期放入 React State；
- 核心交互在普通办公电脑和常见移动设备上保持可用。

MVP 不追求每个性能分数满分，但不能用“以后优化”掩盖明显卡顿、内存泄漏和页面冻结。

## 20. 日志、监控和产品分析

### 20.1 前端错误信息

至少保留：

- 时间；
- 页面和功能；
- 错误码；
- 请求 ID 或任务 ID；
- 应用版本；
- 是否可恢复。

不得默认上传用户完整输入、生成内容、私密文件或访问凭证。

### 20.2 产品埋点

只有在 PRD 或指标方案明确后才实施。事件名称应表达业务行为，例如：

- `generation_submitted`；
- `task_confirmation_completed`；
- `artifact_downloaded`；
- `generation_failed`。

埋点不能阻塞核心操作；埋点失败不能导致生成任务失败。

## 21. 测试与真实预览

### 21.1 最低自动检查

每个可交付阶段至少执行：

```bash
npm run lint
npm run typecheck   # 项目如无该脚本，应通过 tsc --noEmit 或等价方式补齐
npm run test
npm run build
```

如果某项暂未配置，AI 应在阶段文档中说明并补齐合理的最低配置，不能直接写“跳过”。

### 21.2 测试分层

| 层级 | 重点 |
|---|---|
| 单元测试 | 状态映射、数据转换、校验、错误归一化 |
| 组件测试 | 表单、按钮状态、空/错/加载、确认交互 |
| 集成测试 | API 适配层与页面业务流程 |
| E2E 测试 | 一个真实用户从进入页面到获得结果的核心闭环 |
| 人工预览 | 视觉、文案、媒体、响应式、浏览器行为 |

### 21.3 核心业务闭环

每个阶段至少有一条可以真正操作的闭环，例如：

```text
进入生成页
→ 填写输入
→ 成功提交
→ 看到任务运行
→ 处理用户确认（如有）
→ 看到最终产物
→ 刷新页面后仍可恢复
```

仅证明按钮能点击、Mock 数据能展示，不算业务闭环。

### 21.4 浏览器人工检查

AI 在交付前必须真实启动项目并检查：

- 页面能否访问；
- 浏览器 Console 是否有错误；
- Network 是否存在失败或重复请求；
- 加载、空、错误、禁用和成功状态；
- 桌面端与移动端布局；
- 弹窗、侧栏、下拉框和滚动；
- 真实后端接口和流式链路；
- 图片、视频、音频和下载；
- 刷新、返回、断网和恢复。

生产构建成功只能证明工程可构建，不能替代真实页面预览。

### 21.5 交付判定

以下任一情况存在时，不得直接宣布“完成”：

- Lint 或类型检查仍有未解释错误；
- 核心接口仍是 Mock；
- 核心页面在目标尺寸不可用；
- 失败状态会丢失用户输入；
- 重复点击会创建多个任务；
- 刷新后正在运行的任务无法恢复；
- Console 持续报错；
- 实现与确认的设计或 PRD 明显不一致。

如确需阶段性带问题交付，必须列出问题、影响、临时处理和后续计划，由产品负责人明确接受。

**关键业务规则未冻结时**（评分公式、判定阈值、话术标准等尚未定稿）：AI 不应因此卡住开发，而应——
- 用临时规则跑通全链路，界面对用户显式标注"模拟/临时"；
- 把规则做成可配置（JSON / 表），业务冻结后只改配置、不改代码；
- 在交付清单中明确列出"哪些业务规则仍待冻结"，不得当作已完成。

### 21.6 前端部署上线（与《AI Agent 产品上线部署手册》配合）

前端（Next.js）是**独立部署产物**，与后端分开部署、各自有访问地址。部署前必须解决：

1. **standalone 输出**：`next.config` 设 `output: "standalone"`，产物只含最小运行时，打包体积从数百 MB 降到几十 MB。不要默认上传整个 `node_modules`。
2. **静态资源补齐**：standalone 目录默认不含 `.next/static`，需 `cp -r .next/static .next/standalone/.next/static`（有 `public` 同理），否则线上样式/字体 404。
3. **构建时环境变量（关键坑）**：`rewrites` 的目标地址在 **build 时** 固化进产物，部署平台的运行时环境变量改不到它。所以"前端指向哪个后端"（如 `BACKEND_URL`）必须在**执行构建命令时**注入，而不是部署后再配。
4. **启动命令**：standalone 用 `node server.js`（端口默认 3000）；未用 standalone 才用 `npm run start`。
5. **前后端是两个应用**：各自部署；前端通过 `rewrites` 同源代理 `/api/*` 到后端，避免 CORS。过渡期两个地址可并存，旧入口保留作兜底。
6. **HTTPS 是硬要求**：涉及麦克风/摄像头/剪贴板等能力的产品，线上地址必须是 `https://`。

具体部署命令与参数见《AI Agent 产品上线部署手册》。

## 22. 分阶段开发原则

不要按“先写完所有页面，再一次性接接口”拆阶段。应按用户可验证的业务闭环拆分。

### 阶段 0：适配与契约

- 阅读 PRD、现有代码和后端文档；
- 输出《前端技术适配声明》；
- 明确路由、页面清单、设计方向和接口契约；
- 建立任务状态表和核心验收路径；
- 标记尚未确认的假设。

### 阶段 1：可运行骨架

- 建立工程、布局、导航、设计变量和通用组件；
- 接通基础环境配置和 API 客户端；
- 完成一个代表页面；
- 确保桌面和移动端基本布局正确；
- 配置 Lint、类型检查、测试和构建。

### 阶段 2：第一条真实闭环

- 完成一个核心输入流程；
- 对接真实创建任务接口；
- 展示队列、运行、成功和失败；
- 展示至少一种真实产物；
- 增加核心 E2E 或等价的可重复验收步骤。

### 阶段 3：Agent 完整交互

- 接入流式输出或轮询；
- 支持等待用户确认；
- 支持取消、重试、断线和刷新恢复；
- 完善多任务、历史记录或任务中心（按 PRD）；
- 覆盖部分成功和未知状态。

### 阶段 4：质量与发布准备

- 完成响应式、无障碍和多媒体检查；
- 处理性能、错误监控和隐私；
- 与真实后端做完整联调；
- 清理 Console、Lint、类型和测试问题；
- 输出发布说明和已知问题。

具体项目可以合并阶段，但每个阶段都应有可运行、可查看、可验收的结果。

## 26. 产品经理验收清单

产品经理不需要看代码，按下面的问题验收即可。

### 产品流程

- 我能否从进入页面一直操作到获得一个真实结果？
- 当前步骤、等待原因和下一步是否清楚？
- 失败后是否知道怎么恢复？
- 刷新页面后，正在执行或已完成的任务是否还在？
- 重复点击是否会创建多个任务或重复扣费？

### 页面体验

- 第一次打开时是否把“加载中”错误显示成“没有数据”？
- 手机和电脑上是否都能完成核心流程？
- 侧栏、弹窗、菜单是否会挡住内容或无法关闭？
- 图片、视频、音频是否真正能预览和下载？
- 文案是否是普通用户能理解的产品语言？

### Agent 特性

- 运行中、等待确认、失败和完成是否明显不同？
- 断网或离开页面后，任务是否能恢复？
- 用户能否看出哪些是最终结果，哪些只是中间过程？
- Agent 需要用户决定时，选项和影响是否清楚？

### 质量

- AI 是否真实启动并预览了项目？
- 是否完成真实后端联调，而不只是 Mock？
- Lint、类型检查、测试和构建是否通过？
- 是否明确列出了仍然存在的问题？

如果以上核心问题没有答案，就不应进入“完成”状态。

## 27. 常见错误做法

### 错误 1：把技术栈手册当成固定版本安装单

问题：不同项目、已有代码和部署环境不同，机械安装会制造冲突。

正确做法：先输出适配声明，再决定实际版本和可选库。

### 错误 2：只写正常成功页面

问题：Agent 产品大部分真实体验发生在等待、运行、失败和恢复过程中。

正确做法：先建立状态矩阵，再写页面。

### 错误 3：前端自己猜任务已经完成

问题：动画走完、计时结束或连接断开，都不能证明后端任务完成。

正确做法：以后端状态和产物为准。

### 错误 4：加载时显示空数据

问题：用户会误以为系统没有模板、任务或项目。

正确做法：明确区分 loading、empty 和 failed。

### 错误 5：默认值不在可选项中

问题：界面可能静默显示另一个模型或配置，实际请求与用户理解不一致。

正确做法：启动时校验默认值、可选项和已保存值的一致性。

### 错误 6：移动端只缩小桌面页面

问题：侧栏、表格、弹窗和固定宽度内容经常遮挡操作。

正确做法：按移动端交互重排，并在真实宽度检查。

### 错误 7：为了复用制造万能组件

问题：组件参数越来越多，任何修改都会影响全站。

正确做法：在重复模式真实出现后再抽象。

### 错误 8：把所有状态放进全局 Store

问题：URL、后端状态、临时状态和用户偏好混在一起，刷新和同步变得不可预测。

正确做法：按本手册的四层状态分类存放。

### 错误 9：把前端隐藏当成权限控制

问题：用户仍然可以直接请求后端接口。

正确做法：前端负责体验，后端负责最终权限校验。

### 错误 10：构建成功就交付

问题：构建无法发现视觉遮挡、断线、媒体失败和错误文案。

正确做法：自动检查与真实浏览器验收缺一不可。

## 28. 从小云雀项目抽象出的通用经验

本手册吸收了小云雀这类 Agent 工作台的实际特点，但不会把它写成只适用于小云雀的规则。

可复用经验包括：

- App Shell、工作区、任务中心、设置页是常见结构，但应按 PRD 选择；
- 普通 API 与 SSE 可能走不同网络路径，必须集中配置并真实验证；
- 任务需要 pending、running、waiting、completed、failed 等明确状态映射；
- 图片、视频和音频产物需要统一展示模型；
- 用户确认是 Agent 工作流的一等状态，不是普通弹窗；
- 移动端侧栏的 CSS 状态和 React 状态必须一致；
- 模板或配置尚在加载时，不能提前显示空状态；
- 默认模型与模型选项必须一致，不能静默替换；
- Lint、类型和浏览器问题属于交付质量，不能被“页面可以打开”掩盖。

这些经验适用于内容生成、数据分析、自动化执行、客服助手等多种 Agent 产品。

## 29. 最终原则

这份手册提供的是“默认路线 + 决策规则 + 质量底线”，不是不可修改的技术圣经。

一个合格的 AI 前端执行过程应做到：

1. 先理解 PRD 和现有项目；
2. 先说明技术适配，再开始编码；
3. 按真实业务闭环拆阶段；
4. 把 Agent 状态、异常和恢复当成核心产品功能；
5. 让后端数据成为业务事实来源；
6. 用统一组件和设计变量保证体验一致；
7. 同时完成自动检查和浏览器真实验收；
8. 对未完成项和技术债保持透明。

产品经理负责明确“用户要完成什么、什么结果算成功”；本手册帮助 AI 决定“前端怎样稳定、清楚、可验证地实现它”。
