# AI 客服／销售对话质检器 MVP 设计规格

> 日期：2026-08-22  
> 状态：已采用默认方案，进入实施准备  
> 依据：产品 PRD、通用技术栈手册、通用前端技术栈手册、产品上线部署手册、Seline Analytics 视觉参考

## 1. 目标与范围

本项目面向销售主管和客服主管。用户通过一个受邀访问码进入产品，选择「销售质检」或「客服质检」，粘贴一段双角色聊天，获得带证据的六维质检报告、主要问题和一条建议回复。

MVP 必须完成以下闭环：

1. 输入邀请码，获得匿名访问资格；不注册账号，不设置密码，不维护用户资料。
2. 选择质检场景并粘贴聊天。
3. 后端解析角色与轮次，调用 LLM，校验结构并确定性计算报告状态和总分。
4. 前端展示总览、六维结论、证据、主要问题、建议回复和限制说明。
5. 用户复制报告并提交「有用／无用」反馈。
6. 每个邀请码最多完成 50 次成功质检。

MVP 不包含批量上传、聊天平台接入、报告历史、原始聊天保存、组织管理、员工排名、绩效决定、企业知识库、国际化和多终端客户端。

## 2. 已固定的产品参数

PRD 中尚未冻结但会阻塞实施的参数，MVP 采用以下可配置默认值：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| 支持语言 | 简体中文，允许夹杂常见英文和数字 | 不承诺完整多语言评分能力 |
| 最小输入长度 | 20 个字符 | 仍须通过双角色与有效往返校验 |
| 最大输入长度 | 12,000 个字符 | 超限时整体拒绝，不静默截断 |
| 最大轮次数 | 200 轮 | 超限时提示精简对话 |
| 模型请求超时 | 60 秒 | 总体超时，不无限等待 |
| 模型结构重试 | 最多 2 次 | 首次失败后最多再调用 1 次 |
| 访问凭证有效期 | 12 小时 | 过期后重新输入邀请码，不产生账号 |
| 邀请码额度 | 50 次成功质检 | 页面访问、校验失败和系统失败不扣 |
| 元数据与反馈保留期 | 90 天 | 定时删除过期匿名数据 |
| 桌面验收宽度 | 1,280 px、1,440 px | 覆盖常见办公窗口 |
| 移动验收宽度 | 390 px、768 px | 核心闭环必须可完成 |
| 浏览器范围 | 当前及前一个主版本的 Chrome、Edge、Safari | 不支持 Internet Explorer |

这些参数通过配置或版本化规则表达。后续调整不改变接口主结构。

## 3. 技术适配声明

### 3.1 产品形态判断

- 产品类型：固定流程的 LLM 分析工具。
- 核心交互：一次同步分析，不需要自治 Agent、多 Agent、工具规划或长期记忆。
- 主要终端：桌面 Web，兼顾移动 Web。
- 开发路径：后端先行。先独立核验访问控制、配额、解析、模型输出和报告契约，再开发正式前端。
- 当前项目状态：新建产品代码；目录中原有 Agent Blueprint 教学代码不属于产品运行时。

### 3.2 采用的默认方案

- Python 3.11、FastAPI、Pydantic、pytest。
- SQLAlchemy + Alembic + SQLite；邀请码、额度流水、匿名分析元数据和反馈之间存在关系、事务和并发修改，已触发关系型数据库模块。
- OpenAI 官方 SDK 的兼容接口；模型名、Base URL、超时和参数全部读取后端环境变量。
- Next.js App Router、React、TypeScript strict、Tailwind CSS、Vitest、React Testing Library、Playwright。
- 后端与前端分别部署到火山引擎 veFaaS，前端通过同源 `/api/*` 代理访问后端。

### 3.3 暂缓和偏离

- 暂缓 PostgreSQL：封闭试点使用单实例 SQLite；需要多实例并发或复杂运营查询时迁移 PostgreSQL。
- 不使用 SSE：PRD 定义一次同步分析，结果必须经过整体一致性校验后才能展示。普通 HTTP 更符合当前交互；若真实模型 P95 超过 60 秒，再改为「提交任务 + 轮询」。
- 不保存完整报告：前端手册的任务恢复规则让位于 PRD 的隐私要求。刷新后邀请码访问状态可以恢复，但聊天与报告不恢复。
- 不使用商业字体 Roobert：使用 Inter Tight 作为标题替代，中文回退到系统字体。
- 不引入 Redis、消息队列、RAG、对象文件存储和全局前端状态库；当前需求没有触发这些模块。生产环境只使用 TOS 备份 SQLite 数据库文件。

### 3.4 强制底线

- LLM API Key、邀请码 Pepper、会话密钥和云凭证只存在于后端秘密配置。
- 原始聊天、原文证据、完整报告、建议回复不写入数据库或日志。
- 所有请求与模型输出均经过结构校验。
- 错误使用统一结构，不向用户暴露堆栈和供应商原始错误。
- 邀请码额度使用数据库事务和预占流水，不能仅靠内存计数。
- 自动化测试不能冒充真实模型冒烟；未配置 LLM API Key 时真实冒烟明确标为待验。

## 4. 总体架构

```text
浏览器
  └─ Next.js Web
      ├─ 邀请码访问页
      ├─ 对话质检工作台
      └─ 同源 /api 代理
           └─ FastAPI
               ├─ 访问凭证与 CSRF
               ├─ 邀请码配额服务
               ├─ 对话解析与输入校验
               ├─ LLM 分析服务
               ├─ 报告一致性校验与确定性计分
               ├─ 匿名元数据与反馈
               └─ SQLAlchemy
                    └─ SQLite（本地与封闭试点）
```

后端采用模块化单体。API 层只处理 HTTP 契约；业务规则放在服务层；模型提示词独立版本化；数据库访问集中在仓储和事务边界中。前端不复制评分、额度或访问权限规则。

## 5. 邀请码访问与 50 次额度

### 5.1 访问方式

产品不出现「注册」「登录」「账号」「密码」概念。页面文案统一为「输入邀请码」「进入质检」「退出访问」。

1. 用户提交邀请码到 `POST /api/v1/access/redeem`。
2. 后端使用 `INVITE_CODE_PEPPER` 对输入做 HMAC-SHA256，在数据库中匹配摘要；数据库不保存邀请码明文。
3. 邀请码有效且仍有额度时，后端写入签名、限时、HttpOnly Cookie `aqi_access`。
4. Cookie 只包含邀请码记录 ID、随机 CSRF 值和过期时间，不包含用户身份。
5. 后续受保护请求同时校验 Cookie、邀请码状态和 `X-CSRF-Token`。
6. 生产环境 Cookie 使用 `Secure`、`HttpOnly`、`SameSite=Lax`；本地开发只关闭 `Secure`。

### 5.2 额度规则

- 一次通过输入校验并进入模型调用的请求先预占 1 次额度。
- 报告完成结构校验并准备返回时，将预占转换为已使用。
- 模型超时、网络失败、非法输出或服务端异常会释放预占，不扣额度。
- 空输入、超限、角色错误、重复请求和无 LLM 配置均不预占额度。
- 第 50 次成功后，新的分析请求返回 `INVITE_QUOTA_EXHAUSTED`；已打开页面仍可查看当前内存中的报告，但不能继续分析。
- 邀请码兑换和页面刷新不扣额度。

### 5.3 并发、崩溃与幂等

- `invite_codes` 同时记录 `used_count` 和 `reserved_count`。
- 预占通过单条条件更新完成：仅当 `used_count + reserved_count < usage_limit` 时递增 `reserved_count`。
- 每次分析必须带 UUID 格式的 `Idempotency-Key`；同一邀请码下相同 Key 只能创建一条流水。
- 重复 Key 返回 `DUPLICATE_REQUEST`，不重复调用模型、不重复扣费。
- 预占流水超过 180 秒仍未完成时视为崩溃遗留；启动时及每次预占前释放。该时长高于 60 秒超时和重试清理窗口。
- 正式使用 SQLite 时固定后端最大实例数为 1。需要横向扩容时，必须先迁移 PostgreSQL。

## 6. 数据设计

### 6.1 `invite_codes`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | UUID 字符串 | 主键 |
| `code_digest` | 64 位十六进制字符串 | HMAC-SHA256 摘要，唯一 |
| `label` | 字符串 | 运营可识别标签，不含人员信息 |
| `usage_limit` | 整数 | 默认 50 |
| `used_count` | 整数 | 成功质检次数 |
| `reserved_count` | 整数 | 正在执行的预占次数 |
| `is_active` | 布尔值 | 可随时停用 |
| `created_at`、`updated_at` | UTC 时间 | 审计字段 |

### 6.2 `analysis_attempts`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | UUID 字符串 | 分析 ID |
| `invite_code_id` | UUID 字符串 | 仅关联邀请码池，不代表用户 |
| `idempotency_key` | UUID 字符串 | 同一邀请码下唯一 |
| `qa_type` | 枚举 | `sales` 或 `customer_service` |
| `quota_status` | 枚举 | `reserved`、`consumed`、`released` |
| `analysis_status` | 可空枚举 | `scored`、`partial`、`unable_to_score` |
| `char_count`、`turn_count` | 整数 | 不含原文 |
| `latency_ms` | 可空整数 | 总耗时 |
| `model_version` | 可空字符串 | 供应商返回或配置模型名 |
| `rubric_version`、`prompt_version` | 字符串 | 可追溯版本 |
| `scored_dimension_count` | 可空整数 | 0–6 |
| `risk_level` | 可空枚举 | 不含风险原文 |
| `error_type` | 可空字符串 | 归一化错误类型 |
| `created_at`、`completed_at` | UTC 时间 | 生命周期字段 |

该表严禁出现聊天正文、证据原句、完整结论、建议回复、姓名、手机号、员工账号或客户账号。

### 6.3 `feedback`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `analysis_id` | UUID 字符串 | 主键并关联分析 |
| `invite_code_id` | UUID 字符串 | 防止跨邀请码修改 |
| `helpful` | 布尔值 | 有用／无用 |
| `reason_code` | 可空枚举 | `evidence_wrong`、`score_unfair`、`reply_unusable`、`context_missing`、`other` |
| `created_at`、`updated_at` | UTC 时间 | 允许一次更新 |

## 7. 后端 API 契约

所有错误使用以下结构：

```json
{
  "error": {
    "code": "INVITE_CODE_INVALID",
    "message": "邀请码无效或已停用",
    "request_id": "req_...",
    "field_errors": {}
  }
}
```

### 7.1 公共接口

| 方法与路径 | 用途 | 关键行为 |
| --- | --- | --- |
| `GET /health/live` | 进程存活 | 不检查 LLM Key |
| `GET /health/ready` | 数据库与迁移就绪 | LLM 未配置时仍允许服务启动，并返回 `llm_configured: false` |
| `GET /api/v1/public-config` | 表单限制与版本 | 不返回秘密和系统 Prompt |
| `POST /api/v1/access/redeem` | 邀请码换访问 Cookie | 返回剩余额度、过期时间和 CSRF Token |

### 7.2 受保护接口

| 方法与路径 | 用途 | 关键行为 |
| --- | --- | --- |
| `GET /api/v1/access/status` | 恢复访问状态 | 返回剩余额度并刷新前端 CSRF 状态 |
| `POST /api/v1/access/leave` | 清除访问 Cookie | 不删除邀请码或统计 |
| `POST /api/v1/analyses` | 创建同步质检 | 需要 `Idempotency-Key`，成功返回完整但不落库的报告 |
| `PUT /api/v1/analyses/{analysis_id}/feedback` | 新增或更新反馈 | 仅允许当前邀请码对应的分析 ID |

`POST /api/v1/analyses` 请求体：

```json
{
  "qa_type": "sales",
  "transcript": "客户：你们这个太贵了。\n销售：我们已经是最低价格了。"
}
```

成功响应除 PRD 报告字段外，还包含：

- `remaining_uses`：本次成功后的剩余额度。
- `request_id`：排错追踪号。
- `processing_ms`：本次总耗时。

## 8. 分析流水线

### 8.1 确定性预处理

1. 规范换行和可见空白，不改变原句内容。
2. 校验字符数、轮次数和附件引用边界。
3. 按行解析 `角色：内容`，生成 `t1`、`t2` 等稳定轮次 ID。
4. 识别恰好一名客户和一名被质检员工。销售场景接受「销售／顾问」，客服场景接受「客服／坐席」；不跨场景偷换角色。
5. 检查至少存在一次客户到员工或员工到客户的有效往返。
6. 将全部聊天内容包装为不可信数据，明确禁止其中的指令改变评分规则或索取系统 Prompt。

### 8.2 模型调用

- 系统 Prompt 独立保存在 `services/prompts/qa_analysis_v1.md`。
- 输入只包含场景、结构化话轮和版本化评分规则。
- 要求模型仅输出 JSON，不输出 Markdown 代码块；解析器仍兼容常见代码围栏。
- Temperature 默认 0.1。
- 网络重试仅用于明确可重试的超时、限流和 5xx；结构失败只允许 1 次修复重试。
- SDK 初始化、网络调用、JSON 解析和校验全部由最外层统一错误边界包裹。

### 8.3 服务端一致性校验

- 六个维度名称必须完整且唯一。
- `scored` 维度必须有 0–100 分、至少一条可定位证据、具体改进动作和置信度。
- `not_applicable` 与 `insufficient_context` 的分数必须为 `null`。
- 证据引用的 `turn_ids` 必须存在；`quotes` 必须逐字出现在对应轮次中。
- 主要问题最多 3 条，且引用已有维度和轮次。
- 总分完全由后端按可评分维度等权平均并四舍五入计算，忽略模型提供的总分。
- 4–6 个可评分维度得到 `scored`；1–3 个得到 `partial`；0 个得到 `unable_to_score`。
- `partial` 与 `unable_to_score` 的 `total_score` 强制为 `null`。
- 无法判断风险时使用 `unknown`，不能用 `none` 冒充。
- 客户明确要求停止联系时，后端用安全收尾回复覆盖任何继续推进建议。

## 9. 前端信息架构与交互

### 9.1 页面

1. `/access`：邀请码访问页。
2. `/`：对话质检工作台，包含输入、分析状态与报告。
3. Next.js 全局错误页和 404 页面。

不提供报告历史页、账户页、成员页和管理后台。

### 9.2 工作台布局

桌面端采用不对称双栏：左侧约 40% 为场景和聊天输入，右侧约 60% 为结果。未生成结果时，右侧展示六维说明和输入示例；分析中展示阶段提示；生成后展示报告。

移动端改为单列：场景选择 → 输入 → 提交按钮 → 报告。提交按钮在键盘弹出时仍可触达，页面不出现横向滚动。

### 9.3 状态矩阵

| 状态 | 界面行为 |
| --- | --- |
| `checking_access` | 只显示访问检查骨架，不短暂闪现邀请码错误 |
| `access_required` | 显示邀请码表单和隐私提示 |
| `idle` | 显示场景、输入说明、字符计数和六维概览 |
| `invalid` | 错误靠近字段，保留输入，不调用后端模型 |
| `submitting` | 禁止重复提交，显示「正在解析并质检」 |
| `succeeded` | 展示 `scored`、`partial` 或 `unable_to_score` 对应报告 |
| `failed` | 保留输入，区分配置、超时、模型和服务错误，提供重试 |
| `quota_exhausted` | 展示额度用尽，不再显示可提交按钮 |
| `access_expired` | 保留当前未提交输入，重新输入邀请码后继续 |

刷新后恢复邀请码访问状态，但不恢复聊天和报告。报告生成后离开页面前显示「结果未保存，请先复制」提示。

## 10. 视觉方向

视觉参考为 Refero 上的 Seline Analytics 风格，但不复制其商标、插画或受保护资产。

- 设计意象：暖纸面上的安静分析台。
- 页面背景：`#fafaf9`。
- 卡片表面：`#ffffff`。
- 主文字：`#0c0a09`；次文字：`#78716c`。
- 边框：`#e8e6e5`；强调色与主操作：`#3ba6f1`；强调浅底：`#c1e1f7`。
- 标题字体：Inter Tight 400/500；正文与 UI：Inter 400/500/600；中文回退 `PingFang SC`、`Microsoft YaHei`、`Noto Sans CJK SC`。
- 卡片圆角 10–16 px，1 px 石色边框，阴影保持轻且少。
- 主按钮使用青蓝填充和胶囊圆角；次按钮使用浅石色表面。
- 每个主要标题最多使用一处青蓝浅底强调，不堆叠强调色。
- 分数不能只靠颜色表达，风险提示必须同时有图标、文字和等级。
- 图标统一使用 Lucide；品牌标记使用原创抽象「对话检查」线形符号。

报告优先级为：报告状态与总分／覆盖度 → 独立风险提示 → 主要问题 → 建议回复 → 六维详情 → 分析限制 → 反馈。

## 11. 安全、隐私与日志

- FastAPI 限制请求体大小并验证 `Content-Type`。
- 允许来源由 `ALLOWED_ORIGINS` 配置；正式前端优先通过同源代理，不开放通配 CORS。
- 所有写请求使用 CSRF Header；邀请码错误返回统一文案，避免枚举有效码。
- 邀请码必须由至少 128 bit 随机数生成，不接受人工可猜短码。
- 访问兑换按来源地址做进程级速率限制；云网关再配置外层限速。日志不保存完整 IP。
- 响应增加 CSP、`X-Content-Type-Options`、`Referrer-Policy` 和合理的缓存控制。
- 请求日志仅包含 request ID、路径模板、状态码、耗时、匿名邀请码记录 ID 的截断摘要和错误类型。
- LLM 请求正文和响应正文不进入应用日志、Sentry Breadcrumb 或分析埋点。
- 日志脱敏测试扫描常见手机号、API Key 前缀和测试原文。

## 12. 部署设计

### 12.1 本地开发

- 后端使用 Python 3.11 虚拟环境，默认端口 8010；当前机器的 8000 端口已被其他进程占用。
- 前端使用 Node.js 活跃 LTS 兼容版本，默认端口 3010；当前机器的 3000 端口已被其他进程占用。
- `.env` 永不提交；`.env.example` 只列键名和安全示例。
- 没有 `LLM_API_KEY` 时应用正常启动，分析接口返回可理解的 `LLM_NOT_CONFIGURED`，不扣额度。

### 12.2 火山引擎 veFaaS

- 后端和前端是两个独立应用，共用 Serverless API 网关。
- 后端启动命令：`python -m uvicorn app.main:app --host 0.0.0.0 --port 8000`。
- 前端使用 Next.js `output: "standalone"`，构建时注入 `BACKEND_URL`，运行 `node server.js`。
- 后端生产数据库位于 `/tmp/data/app.db`，设置最小实例 1、最大实例 1。
- 每 5 分钟把 SQLite 一致性快照上传到 TOS；veFaaS 角色模式在首个携带平台 STS 请求头的请求中恢复缺失数据库，完成回读快照前不开放业务流量。
- 环境变量先于首次发布配置。至少包含 `ENVIRONMENT`、`DATABASE_URL`、`SESSION_SECRET`、`INVITE_CODE_PEPPER`、`INVITE_CODES`、`LLM_*` 和 TOS 配置；TOS 使用函数角色短期凭证，不在环境变量保存长期 AK/SK。
- `.vefaasignore` 排除 `.env`、`.venv`、`data`、缓存、测试产物和 `.vefaas`。
- 需要多实例或请求量超过单实例承载能力时，停止扩容并先迁移 PostgreSQL。

实际创建付费云资源前必须向产品经理说明费用，并取得当次确认。云账号注册、实名认证、AccessKey 和网关控制台操作需要产品经理配合。

## 13. 测试与验收

### 13.1 后端自动化

- 角色与轮次解析：合法销售、合法客服、空白、单角色、混乱角色、多人、超长、提示注入。
- 报告校验：六维完整性、证据轮次、原句匹配、分数状态、总分、覆盖度、风险和建议回复边界。
- 邀请码：错误码、停用码、过期访问凭证、CSRF、Cookie 属性。
- 额度：50 次成功后拒绝第 51 次；并发预占不超限；失败释放；崩溃预占过期释放；重复 Key 不重复扣减。
- 隐私：数据库、结构化日志和错误响应中不存在测试聊天正文、证据和建议回复。
- API：统一错误结构、request ID、健康检查、反馈新增和更新。
- Alembic：从空库升级到最新版本并可启动应用。

### 13.2 前端自动化与浏览器检查

- ESLint、TypeScript、Vitest、React Testing Library、生产构建全部通过。
- Playwright 使用真实 FastAPI 测试服务和注入的假模型，覆盖：邀请码 → 选择场景 → 提交 → 报告 → 复制 → 反馈。
- 覆盖邀请码错误、输入错误、部分结果、无法评分、模型失败、重试、额度用尽和访问过期。
- 在 390、768、1,280、1,440 px 检查布局、焦点、键盘操作、对比度和横向滚动。
- 浏览器 Console 无未解释错误，Network 无重复模型请求。

### 13.3 双层模型验收

第一层使用依赖注入的假模型，离线验证全部工程行为。第二层必须在用户写入真实 `LLM_API_KEY` 后，用 PRD 示例完成至少一次真实输入 → 模型 → 校验 → 返回的冒烟，并记录模型、耗时、重试和结果质量。未执行第二层前，不声称模型效果验收完成。

### 13.4 上线验收

- HTTPS 地址可访问。
- 无访问 Cookie、错误邀请码和正确邀请码分别得到预期结果。
- 成功质检后额度减少 1；失败不减少。
- 前端通过同源 `/api` 正常访问后端。
- SQLite 备份存在，并通过一次隔离恢复演练验证可用。
- 结构化日志能用 request ID 串联，且不含聊天正文和秘密。
- 手机和桌面浏览器均可完成核心闭环。

## 14. 实施阶段

### 阶段 1：后端 MVP

实现数据库、邀请码访问、额度事务、解析、模型适配、Prompt、报告校验、反馈、迁移、日志和测试。完成离线自动化核验后才进入前端。

### 阶段 2：正式 Web 前端

依据已冻结 API 契约实现邀请码页和质检工作台，完成响应式、无障碍、组件测试、E2E 和真实浏览器核验。前端不修改后端评分规则。

### 阶段 3：上线准备与部署

实现 veFaaS 配置、SQLite/TOS 备份恢复、部署排除、结构化日志和运行手册。先完成本地部署预检；取得云账号所需配合和费用确认后创建资源、部署并执行线上验收。

## 15. 需求覆盖结论

本规格覆盖 PRD 的全部 P0 功能：受邀访问、场景选择、文本输入与校验、角色解析、六维分析、报告状态、确定性总分、风险提示、主要问题、证据、改进建议、建议回复、限制说明、失败重试、隐私处理、复制报告和有用性反馈。

明确未完成条件只有外部输入：真实 LLM API Key 用于模型冒烟，以及火山引擎账号、权限和费用确认用于创建云资源。这些不阻塞本地开发和离线核验，但会在对应验收点如实标记。
